### Personal task, schedule & project-tracking system (Notion replacement)

**Owner:** Benedict Isaac
**Target host:** workspace.benedictisaac.dev
**Status:** v1 build spec
**Note on design:** This PRD intentionally contains **no color, typography, or visual-style specification**. Visual design is handled separately in Stitch using Benedict's own UI preferences. This document defines structure, data, and behavior only.

## 1. Overview

Workspace is a single-user, installable web app (PWA) that replaces Notion as Benedict's daily task and project operating system. It manages three layers of information — a recurring weekly schedule, a pool of active long-running projects/roles ("Threads"), and one-time tasks — and syncs bidirectionally with Google Calendar. The same document is used to (a) generate the UI in Stitch and (b) brief a coding agent to build the working software.

### 1.1 Goals
- Replace the Notion system currently in use, without losing the two-layer structure it had (recurring daily/weekly schedule + one-time task backlog).
- Make daily use frictionless on both mobile and desktop, including offline.
- Make the whole structure fully editable — nothing hardcoded. Threads, frequencies, and the weekly grid can all be changed by the user at any time.
- Support fast one-time task capture.
- Track completion over time per Thread (streaks/analytics) and support quarterly goal-setting.
- Two-way sync with Google Calendar.

### 1.2 Non-goals (v1)
- No multi-user support or account system beyond the single owner.
- No LLM-powered features in v1 (see §8 — designed for, not built now).
- No visual design decisions — deferred to Stitch.

## 2. Core Concepts / Information Architecture

Workspace is built around three linked concepts:

### 2.1 Threads (Active Threads — replaces flat "Layer 2a" list)
A **Thread** is any standing project, role, learning track, or recurring effort — e.g. "ECAPs R&D," "AWS Builder Group Technical Lead," "Job & gig applications." Threads are long-lived and rarely "completed" — they generate tasks over time.

Each Thread has:
- `name` (string)
- `category` (enum, user-editable list — starting values: Role/Program, Active Build, Learning Track, Application/Outreach, Other)
- `frequency` (enum: `daily`, `multiple` (appears several times/week), `weekly` (once/week), `fixed-day` (tied to a specific day, e.g. AWS = Saturday))
- `fixedDay` (optional — day of week, only used if frequency = `fixed-day`)
- `status` (enum: `active`, `parked`/idea-stage, `archived`)
- `notes` (free text, optional)

Threads are what the weekly grid (§2.3) is built from. Editing a Thread's frequency or status automatically reshapes the auto-generated weekly grid going forward (see §5.2).

### 2.2 Tasks
Two kinds of tasks, one underlying schema:

**a) Thread task** — an atomic to-do generated for/from a Thread on a given day (e.g. "ECAPs — sensor calibration test" under the ECAPs Thread on Thursday).

**b) One-time task** — a standalone to-do not tied to any Thread. Belongs to Layer 2b. Quick-add is a first-class action available from anywhere in the app (see §5.3).

Shared Task fields:
- `title` (string)
- `threadId` (nullable — null for pure one-time tasks)
- `date` (the day it's scheduled for)
- `timeBlock` (enum: `morning`, `afternoon`, `evening`, `unscheduled`)
- `status` (enum: `pending`, `done`, `skipped`)
- `completedAt` (timestamp, nullable)
- `calendarEventId` (nullable — set if pushed to/pulled from Google Calendar)
- `source` (enum: `manual`, `auto-generated`, `google-calendar`)

### 2.3 Weekly Grid (Layer 1)
The Mon–Sun structure Benedict and Claude designed together: each day has Morning/Afternoon/Evening blocks. The grid is **auto-generated by default** from the active Threads' frequencies (daily Threads appear every day; "multiple" Threads are distributed several times across the week; "weekly" Threads appear once; "fixed-day" Threads lock to their day) — but every individual day and every individual slot is directly editable/overridable by the user without breaking the auto-generation logic for future weeks.

- Regeneration happens per week (a "week" is the unit that gets (re)built from current Thread definitions).
- Manual overrides for a specific date persist and are not clobbered by regeneration unless the user explicitly resets that day.
- Adding, removing, or changing a Thread's frequency updates the generation logic for future (not past) weeks.

### 2.4 One-time Task Backlog (Layer 2b)
A flat, filterable list of one-time tasks not yet scheduled to a specific day, plus a fast-capture entry point. Tasks here can be dragged/assigned into a day's grid, or left as pure backlog.

### 2.5 Wishlist
A simple standalone list, separate from Threads/Tasks, for purchase items to reference when funds are available. Fields: `item` (string), `note` (optional), `acquired` (boolean).

### 2.6 Goals & Analytics
A quarterly goals view (free text or lightweight structured goals, editable) plus a completion analytics view:
- Per-Thread completion count/streak (e.g., "12/14 ECAPs tasks completed this month," "5-day streak on Python").
- Overall daily-completion streak (did you touch every `daily`-frequency Thread today).
- Simple weekly/monthly rollup, not deep BI — this is a motivational mirror, not a reporting tool.

## 3. Screens / Views

These are functional descriptions for Stitch — no visual styling implied.

1. **Today view** (default/home screen) — Morning/Afternoon/Evening blocks for the current day, each showing that day's Thread-generated tasks and one-time tasks, with checkboxes. Quick-add entry point always visible.
2. **Week view** — the Mon–Sun grid, all days visible/scrollable, each showing its blocks. Supports drag/edit of tasks between blocks and days.
3. **Threads view** — list/manage all Threads: create, edit frequency/category/status, archive. Filterable by category.
4. **Backlog view** — Layer 2b one-time tasks not yet assigned to a day.
5. **Wishlist view** — simple checklist of purchase items.
6. **Goals & Analytics view** — quarterly goals + per-Thread/overall streak and completion stats.
7. **Settings view** — Google Calendar connection status/controls, data export, weekly regeneration controls (reset a week to auto-generated state).

## 4. Features (functional detail)

### 4.1 Task management
- Create, edit, delete, complete/uncomplete any task (Thread task or one-time).
- Quick-add: single input field, available globally (e.g., a persistent "+" action), that creates a one-time task with minimal friction — defaults to today/unscheduled block, editable after.
- Drag-and-drop or equivalent to move tasks between time blocks/days.
- Bulk actions: mark all done in a block, clear a day.

### 4.2 Thread management
- Full CRUD on Threads.
- Changing frequency/fixedDay immediately affects future auto-generation.
- Archiving a Thread stops it from generating new tasks but preserves history for analytics.

### 4.3 Weekly grid auto-generation
- Generation logic (runs when a new week starts, or on-demand "regenerate" per day/week):
  - `fixed-day` Threads → placed on their specified day.
  - `daily` Threads → one task placed every day.
  - `multiple` Threads → distributed across the week, avoiding clustering all on one day where possible, targeting roughly 3x/week unless the user sets a different target.
  - `weekly` Threads → placed once, distributed so no single day is overloaded.
- Manual edits to a specific day are preserved; regeneration only fills/creates going forward, never silently overwrites a day the user has hand-edited unless the user explicitly triggers "reset this day/week."

### 4.4 Google Calendar integration (two-way)
- OAuth2 connection to Benedict's Google account (Settings screen).
- **Push:** scheduled tasks (with a day + time block, or explicit time if the user sets one) are created/updated as Google Calendar events; completing/deleting a task updates/removes the linked event.
- **Pull:** events from Benedict's Google Calendar appear inside the relevant day's view (e.g., under an "Events" section per day) so his real calendar and Workspace stay visually unified. Pulled events are read-context by default (not converted into editable Tasks unless he explicitly imports one).
- Sync conflict handling: last-write-wins is acceptable for v1; no need for complex merge logic.

### 4.5 Offline / PWA
- Installable on mobile and desktop (manifest + service worker).
- Core read/write of Today view and quick-add must work offline; changes sync to MongoDB Atlas and Google Calendar once back online.
- Local caching of the current week's data for offline access.

### 4.6 Editing & flexibility (cross-cutting requirement)
- Every entity (Thread, Task, Wishlist item, Goal) is editable and deletable through the UI — nothing requires direct database access to change.
- No hardcoded thread list, day structure, or block names in the frontend — all driven by data so the system can evolve as Benedict's actual work does.

## 5. Data Model (MongoDB collections)

**threads**
```
{ _id, name, category, frequency, fixedDay, status, notes, createdAt }
```

**tasks**
```
{ _id, title, threadId (nullable), date, timeBlock, status, completedAt, calendarEventId (nullable), source, createdAt }
```

**wishlistItems**
```
{ _id, item, note, acquired, createdAt }
```

**goals**
```
{ _id, period ("Q4-2026"), text, createdAt }
```

**calendarSync**
```
{ _id, googleAccountId, accessToken, refreshToken, lastSyncedAt }
```

**settings**
```
{ _id, weeklyGenerationRules (overrides to default distribution logic), timezone }
```

## 6. Tech Stack

- **Frontend:** Vite + React, PWA via `vite-plugin-pwa`.
- **Backend:** Node.js + Express, Mongoose ODM.
- **Database:** MongoDB Atlas.
- **Auth:** none for v1 (single user); reserve a lightweight passcode/env-based gate as an easy add since the app is publicly hosted at a real domain.
- **Calendar:** Google Calendar API (OAuth2, two-way sync as in §4.4).
- **Hosting:** frontend + serverless API (e.g., Vercel) or a small always-on Node server (e.g., Render/Railway) — Benedict to confirm final hosting choice; either works with the schema above.
